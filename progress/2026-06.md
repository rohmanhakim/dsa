### LC 72 - Edit Distance (Medium)

**Pattern:** 2D Dynamic Programming (String Editing)

**Approach:** Classic DP table where `dp[i][j]` = minimum operations to convert `word1[0..i-1]` to `word2[0..j-1]`. Table is `(m+1) x (n+1)` with base cases for empty string conversions (row 0 = insertions, column 0 = deletions).

**Recurrence:**
- If characters match: `dp[i][j] = dp[i-1][j-1]` (no operation)
- If characters differ: `dp[i][j] = 1 + min(dp[i-1][j-1], dp[i-1][j], dp[i][j-1])` (replace, delete, insert)

**Key Learning:**
- Understood the 2D DP table structure for edit distance
- Clarified that `i == j` (index positions being equal) is irrelevant — what matters is whether the actual characters match
- Learned to include all three operations (insert, delete, replace) in the mismatch case
- Remembered to handle the match case explicitly (carry forward diagonal value)

**Honest Self-Assessment:**
- Solved with guidance, not independently. Guessed recurrence from the example table rather than deriving it from the invariant.
- Need to practice the habit: define the invariant first, then derive the recurrence from it, then verify with examples.

- LC 5 - Longest Palindromic Substring (2D DP, different recurrence)
- LC 64 - Minimum Path Sum (2D DP, simpler)

### LC 1967 - Number of Strings That Appear as Substrings in Word (Easy)

**Pattern:** String Manipulation / Brute Force

**Approach:** Built a map of all substrings of `word` by iterating over all substring lengths and positions, then checked each pattern against the map for O(1) membership lookup.

**Actual Complexity:**
- Time: O(n³) — O(n²) substrings, each hash cost O(length)
- Space: O(n²) — storing all substrings in a map

**Simpler Approach Identified:**
```go
import "strings"

func numOfStrings(patterns []string, word string) int {
    count := 0
    for _, p := range patterns {
        if strings.Contains(word, p) {
            count++
        }
    }
    return count
}
```
- Time: O(m * n * k) where m = patterns, n = word length, k = avg pattern length
- Space: O(1)

**Key Learning:**
- Recognized the solution is over-engineered — built a map of all substrings when `strings.Contains` achieves the same result in simpler code
- Discussed when to use built-in helpers vs. custom implementations in interviews/contests:
  - CP contests: always allowed, expected
  - Interviews: allowed unless the problem specifically asks to implement the algorithm
  - General rule: use the simplest tool, but be ready to explain the underlying algorithm
- Key insight: "Before coding, ask: what's the minimum I need to compute?"

**Weakness Identified:**
- Over-engineering / overthinking — tendency to build data structures (maps, arrays) when a simpler built-in function would suffice
- Need to practice: identify what the problem *actually* asks for before starting to code

**Minor Code Quality Notes:**
- `subs[p] == true` → just use `if subs[p]`
- `subs[word] = true` at start is redundant (loop generates it)
- `fmt` import unnecessary for core logic

**Follow-up: Handling Large Constraints**

When constraints are large (e.g., n, m ≤ 10⁵), the approach needs to change:
- **Aho-Corasick** — multi-pattern matching in O(n + m*k + z) time. The gold standard for many patterns.
- **Trie + scan** — insert patterns into a trie, scan word once. Great when patterns are short.
- **Rabin-Karp** — rolling hash for O(n + k) average pattern matching.

General constraint-to-algorithm mapping:
- n ≤ 10⁴ → O(n²) brute force is fine
- n ≤ 10⁵ → O(n log n) — sorting, binary search, two pointers
- n ≤ 10⁶ → O(n) — sliding window, hash map, BFS/DFS

**Key Insight:** When constraints are large, ask: "Can I avoid checking each pattern separately?" If yes, use a data structure (Trie, automaton) to process everything in one pass.

**Status:** Solved ✓ (independently)

**Time complexity:** O(n³) (over-engineered, can be O(m*n*k) with `strings.Contains`)
**Space complexity:** O(n²) (over-engineered, can be O(1))

### LC 14 - Longest Common Prefix (Easy)

**Pattern:** String Manipulation / Horizontal Scanning

**Approach:** Start with the first string as the prefix. For each subsequent string, compare characters one by one and shrink the prefix to the matching portion.

**Complexity:**
- Time: O(S) — S = sum of all characters across all strings
- Space: O(1) — only a few variables (prefix and index)

**Key Learning:**
- Successfully solved independently
- Initial solution worked but was over-engineered (used `longest`, `prev`, and `math.MaxInt` unnecessarily)
- Simplified by removing redundant state — only `pref` and `curr` are needed
- Reinforced the "over-engineering" weakness: always ask "what's the minimum state I need to track?"
- Minor follow-up: `if preflen < len(pref)` guard is unnecessary since `pref[:preflen]` is a no-op when `preflen == len(pref)`

**Alternative Techniques (Large Constraints):**
- **Vertical Scanning** — O(min_len × n): compare character by character across all strings at each position. Better average case when early mismatch is likely.
- **Sorting** — O(S log S + min_len): sort strings, compare only first and last. Elegant, minimal code.
- **Trie (Prefix Tree)** — O(S) build + O(L) query: build trie from all strings, traverse longest single-child path. Best when reusing structure for multiple prefix queries.
- **Binary Search on Prefix Length** — O(S × log(min_len)): binary search on candidate length, check all strings at each candidate.

**Status:** Solved ✓ (independently, with post-solution refinement)

**Time complexity:** O(S)
**Space complexity:** O(1)

### LC 208 - Implement Trie (Prefix Tree) (Medium)

**Pattern:** Trie / Prefix Tree

**Approach:** Standard trie with 26-child array per node. Each node stores `children [26]*Node` and `isEnd bool`. Navigation during insert/search/startsWith is character-by-character: for each character, follow or create the child at index `ch - 'a'`.

**Complexity:**
- Time: O(L) per operation where L = length of word/prefix
- Space: O(N * L) total where N = number of words, L = avg length

**Key Learning:**
- First time implementing a trie from scratch — understanding the core navigation pattern
- Initially tried to build a compressed trie (radix tree) with substring storage and LCP computation — over-engineered. Recognized this and pivoted to the standard 26-child approach
- Key insight: all three operations (insert, search, startsWith) share the same navigation pattern. The only difference is what you check at the end:
  - Insert: create nodes as needed, mark `isEnd = true`
  - Search: return false on nil child, return `isEnd` at the end
  - StartsWith: return false on nil child, return `true` if all chars found (no `isEnd` check)
- Bug caught: in StartsWith, initially forgot to advance `curr` after nil check — was checking the same node's children for every character

**Weakness Reinforced:**
- Over-engineering — started with a complex compressed trie when the standard trie was sufficient. Need to ask: "Is this optimization actually needed for the problem?"

**Status:** Solved ✓ (with guidance on navigation pattern)

**Time complexity:** O(L) per operation
**Space complexity:** O(N * L) total
