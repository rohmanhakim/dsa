### LC 72 - Edit Distance (Medium)

**Pattern:** 2D Dynamic Programming (String Editing)

**Approach:** Classic DP table where `dp[i][j]` = minimum operations to convert `word1[0..i-1]` to `word2[0..j-1]`. Table is `(m+1) x (n+1)` with base cases for empty string conversions (row 0 = insertions, column 0 = deletions).

**Recurrence:**
- If characters match: `dp[i][j] = dp[i-1][j-1]` (no operation)
- If characters differ: `dp[i][j] = 1 + min(dp[i-1][j-1], dp[i-1][j], dp[i][j-1])` (replace, delete, insert)

**Key Learning:**
- Understood the 2D DP table structure for edit distance
- Clarified that `i == j` (index positions being equal) is irrelevant — what matters is whether the actual characters match
- Learned to include all three operations (insert, delete, replace) in the mismatch case
- Remembered to handle the match case explicitly (carry forward diagonal value)

**Honest Self-Assessment:**
- Solved with guidance, not independently. Guessed recurrence from the example table rather than deriving it from the invariant.
- Need to practice the habit: define the invariant first, then derive the recurrence from it, then verify with examples.

### LC 1967 - Number of Strings That Appear as Substrings in Word (Easy)

**Pattern:** String Manipulation / Brute Force

**Approach:** Built a map of all substrings of `word` by iterating over all substring lengths and positions, then checked each pattern against the map for O(1) membership lookup.

**Actual Complexity:**
- Time: O(n³) — O(n²) substrings, each hash cost O(length)
- Space: O(n²) — storing all substrings in a map

**Simpler Approach Identified:**
```go
import "strings"

func numOfStrings(patterns []string, word string) int {
    count := 0
    for _, p := range patterns {
        if strings.Contains(word, p) {
            count++
        }
    }
    return count
}
```
- Time: O(m * n * k) where m = patterns, n = word length, k = avg pattern length
- Space: O(1)

**Key Learning:**
- Recognized the solution is over-engineered — built a map of all substrings when `strings.Contains` achieves the same result in simpler code
- Discussed when to use built-in helpers vs. custom implementations in interviews/contests:
  - CP contests: always allowed, expected
  - Interviews: allowed unless the problem specifically asks to implement the algorithm
  - General rule: use the simplest tool, but be ready to explain the underlying algorithm
- Key insight: "Before coding, ask: what's the minimum I need to compute?"

**Weakness Identified:**
- Over-engineering / overthinking — tendency to build data structures (maps, arrays) when a simpler built-in function would suffice
- Need to practice: identify what the problem *actually* asks for before starting to code

**Minor Code Quality Notes:**
- `subs[p] == true` → just use `if subs[p]`
- `subs[word] = true` at start is redundant (loop generates it)
- `fmt` import unnecessary for core logic

**Follow-up: Handling Large Constraints**

When constraints are large (e.g., n, m ≤ 10⁵), the approach needs to change:
- **Aho-Corasick** — multi-pattern matching in O(n + m*k + z) time. The gold standard for many patterns.
- **Trie + scan** — insert patterns into a trie, scan word once. Great when patterns are short.
- **Rabin-Karp** — rolling hash for O(n + k) average pattern matching.

General constraint-to-algorithm mapping:
- n ≤ 10⁴ → O(n²) brute force is fine
- n ≤ 10⁵ → O(n log n) — sorting, binary search, two pointers
- n ≤ 10⁶ → O(n) — sliding window, hash map, BFS/DFS

**Key Insight:** When constraints are large, ask: "Can I avoid checking each pattern separately?" If yes, use a data structure (Trie, automaton) to process everything in one pass.
