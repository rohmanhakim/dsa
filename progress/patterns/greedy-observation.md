Model an operation's net effect as a formula, then optimize. Key insight: the net effect of a trade (or any complex operation) is often much simpler than the operation itself — the removed part is restored (net zero) and the actual gain comes from a smaller, identifiable component.

## Lessons

- **LC 3499:** Built complex region-scanning mechanism (3 nested loops per transition point + special cases) when the editorial's observation (gain = sum of adjacent zero-block lengths) reduces the problem to a simple one-pass scan. Time: 1:55:00 vs 30-min target. **Key lesson:** Before building complex scanning logic, spend 5 minutes tracing through one example and ask: "What is the net effect of this operation?" If the net effect can be expressed as a formula, use the formula — don't simulate step by step.
- **LC 3501 (guided, 5+ hours):** Same observation extended to multiple range queries. The core formula (cnt1 + bestGain) was already internalized from LC 3499 — difficulty was purely in range query implementation. 10+ edge case bugs: boundary truncation, binary search predicate direction, off-by-one in slice endpoints and RMQ formula, sparse table built per-query causing TLE. **Key lesson:** When extending a single-query solution to multiple queries, separate boundary-finding from computation — compute all boundary values (i, j, zzi, zzj) FIRST, then compute the three cases.
- **LC 3702 (guided, sev 3):** XOR subsequence problem. Initially jumped to DP (running XOR subsequence with 2D DP table) when the problem is a pure observation/classification problem. After hint, recognized the 3-case structure: totalXor ≠ 0 → n; totalXor = 0 + non-zero element exists → n-1; all zeros → 0. Solution is O(n) time, O(1) space. **Key lesson:** Before building any DP table, ask: "Can the answer be determined by a single pass of observation?" If the operation (XOR, sum, etc.) is associative/commutative, the order of elements doesn't matter — think about total vs. exclusion, not about building up subsequences.
- **LC 2029 (guided, sev 3):** Two-player stone game where sum % 3 == 0 means the picker loses. Initially classified as minimax DP (state = subset × turn × sum mod 3), which is infeasible. After guidance: (1) reduce to mod-3 remainders (type 0/1/2), (2) recognize type-0 stones are "turn switches" that don't affect the sum, (3) after first pick, the forced sequence is largely determined. Even cnt[0]: type-0 cancel → Alice wins iff both types exist. Odd cnt[0]: Bob gets escape via type-0 → Alice wins only if |cnt[1]-cnt[2]| > 2. **Key lesson:** For games where the losing condition depends on a modular property, the state collapses to counts — don't reach for DP. Also learned that "type-0 as turn switch" is not a simple global flip; Bob uses them as **escapes** from forced sequences.
- **LC 1386 (ind, sev 1, 1:45:34):** Cinema seat allocation. Correctly identified the core observation: left [2-5] and right [6-8] blocks are non-overlapping (can coexist for 2 groups), mid [4-7] overlaps both (fallback for 1 group). Time: 1:45:34 vs 30-min target. Most time spent on edge cases through submit-WA-debug cycles. **Key lesson:** For observation problems where the core insight is simple, invest time in pre-submit edge case tracing (all reserved → 0, none reserved → 2, only mid blocked → 1) rather than iterative submit-debug. The observation was solid; the iteration logic (sorting, row-by-row scanning) introduced bugs that could have been caught by 2 minutes of manual tracing.
- **LC 3720 (guided, sev 3):** Lexicographically smallest permutation greater than target. Started with DFS backtracking generating all permutations — O(n!) on n=300. After guidance: greedy left-to-right construction with feasibility check. **Key lesson — constraint check is step 0:** n=300 → O(n²) target, O(n!) is instant TLE. Always check constraints before choosing an algorithm family. Also learned the **greedy construction sub-pattern**: build answer left-to-right, at each position try to match target[i] (feasibility check: can largest suffix of remaining chars beat the target suffix?), if infeasible go bigger + fill ascending. Once you go bigger, the rest is deterministic — no backtracking needed.
- **LC 3734 (guided, sev 3):** Lexicographically smallest palindromic permutation > target. Built complex full-string approach (n positions) instead of recognizing the **left-half reduction**: a palindrome = left half + middle + reverse(left half), so only ⌊n/2⌋ positions need decisions. After guidance: left-half greedy construction with largest-completion feasibility check. **Key lessons:**
  1. **Reduce before coding:** Recognize symmetry/constraints that shrink the decision space. Here, palindrome symmetry halves the problem from n to n/2.
  2. **Feasibility check = largest completion:** If the LARGEST palindrome from a prefix can't beat target, no completion can. This is the same pattern as LC 3720.
  3. **Bug: running vs final state for mid detection.** Determined middle character inside the counting loop using running frequency (which flips odd/even per occurrence). Must use the **final** frequency array after the loop ends. General lesson: don't derive static properties from intermediate loop states.
  4. **Bug: missing "no placement" detection.** When the greedy inner loop tries all chars and none works, the outer loop continued silently. Always detect and handle the "no feasible character" case explicitly.
- **LC 2948 (guided, sev 3):** Transitive swap grouping problem. Correctly identified sorting + segment detection approach (walk sorted array, break groups when consecutive difference > limit). Failed at final assembly: used global sorted indices for in-place swaps instead of pairing sorted values with sorted original indices within each group. **Key lessons:**
  1. **Transitive swapping = grouping:** If A↔B and B↔C within limit, all three form an interchangeable group (any permutation achievable). Sorting values and checking consecutive diffs is the standard way to find these groups.
  2. **Group assembly pattern:** Given a group of {values} and their {original indices}, sort the indices, then assign values in order (smallest value → smallest index). This is a reusable sub-pattern for "assign best to best position" problems.
  3. **Gap in connecting data to output:** Had the right data structures (segments with values and indices) but couldn't bridge to final array construction. Practice need: given intermediate grouped data, explicitly state what the output assignment should look like before coding the assembly step.
