- **Binary Search** — Solved 5 problems (LC 35, LC 704, LC 34, LC 278, LC 153). **5/5 consecutive independent-within-goal.** Understand the two templates: **closed interval** (`left <= right`, `right = len(nums) - 1`) for searching known elements, and **half-open interval** (`left < right`, `right = len(nums)`) for lower bound / insertion point. Key insight: never overshoot the answer — if `mid` could be the answer, assign `right = mid` (not `mid - 1`). The closed vs half-open distinction determines all other choices (loop condition, init, shrink direction). Applied half-open template to range-finding (LC 34): two back-to-back binary searches with only the comparison operator changed. Applied half-open template to rotated sorted array search (LC 153): compare `nums[mid]` with `nums[right]` to determine which half contains the minimum — when `mid > right`, minimum is to the right; when `mid ≤ right`, minimum is at mid or to the left. Template naturally handles the unrotated case. **Speed improving:** LC 35: 14:59, LC 704: 7:04, LC 34: 28:49, LC 278: 5:40, LC 153: 17:48 — all within goal time.

### Patterns In Progress
- **Prefix Sum** — Three guided applications: LC 3756 (range sum with digit concatenation), LC 3532 (range emptiness for connectivity queries), and LC 3534 (component connectivity via sorted adjacency breaks). Core idea: precompute cumulative values in O(n) to answer range queries in O(1). Two variants learned:
  - **Variant A (range sum):** 1-indexed arrays with sentinel at index 0, query on [l,r] uses `pref[r+1] - pref[l]`. For non-trivial functions, precompute powers of the base.
  - **Variant B (range emptiness):** Prefix sum of boolean flags (breaks/gaps), query [u,v] checks `prefix[v] - prefix[u] == 0`. Useful when sorted array + connectivity queries imply contiguous components.
  - **Still requires guidance to recognize** — need to internalize: when constraints show n=10^5 and q=10^5, O(nq) is too slow, think prefix sums.
- **Sliding Window** — 2 DB sessions (LC 1358 was guided but never logged to DB). **2/5 consecutive severity ≤ 1** (LC 3 severity 1, LC 209 severity 0), **2/3 distinct days**. Understand two sub-variants:
  - **Longest valid** (expand when valid, shrink when invalid): LC 3 — longest substring without repeating characters. Hash map of last-seen indices for O(1) duplicate detection. Key trick: `left = max(left, seen[char]+1)` handles stale entries.
  - **Shortest valid** (shrink when valid, track min): LC 209 — minimum subarray sum ≥ target. Standard template: `for right / while sum >= target { update answer; shrink left }`.
  Core insight: when a window is valid, all extensions are also valid (superset property). Two counting perspectives: count extensions right (`n-right`) or count extensions left (`left`).
  **LC 3 lesson:** Used `strings.Contains` for duplicate detection (O(n²)). Hash map is O(n).
  **LC 209 lesson:** Non-standard init (left=0, right=1, sum=nums[0]) added unnecessary complexity (`found` boolean, `if right < n` guard, slice allocation). Adopt standard template: both pointers at 0, sum at 0, `right - left` for length.
  **Note:** LC 1358 session was never logged to DB — needs retroactive insert if full history is desired.
- **Binary Search on Answer ("maximize the minimum")** — Applied twice with guidance: LC 2812 (BFS + binary search) and LC 3620 (topo sort + DP + binary search). Core idea: binary search on the answer + feasibility check. Monotonicity property: if threshold `mid` works, then `mid-1` also works. The feasibility check can use any reachability/search algorithm (BFS, DFS, DP). **Still requires guidance to recognize** — need to internalize: ask "am I maximizing the minimum?" before choosing an approach.
- **DAG Topo Sort + DP** — First application via LC 3620 (with guidance). Post-order DFS topo sort: push node after visiting all neighbors, pop from stack = topological order (no reverse needed). Forward DP: `dp[v] = min over predecessors u of (dp[u] + edge_cost(u,v))`. Combined with binary search for optimization problems on DAGs. **Needs independent practice.**
- **BFS / Connected Component Traversal** — Solved LC 2492 with BFS. Second application via LC 2685 (guided, severity 3). Key template learned: `if !visited[neighbor] { enqueue }` instead of `if visited[neighbor] { continue }` — separates edge processing from enqueue control. Understand when BFS suffices (component-level properties like min/max edge weight) vs when backtracking is needed (enumerating distinct paths). **LC 2685 lesson:** For checking if a connected component is complete, use the degree property — a component with `k` vertices is complete iff every vertex has degree `k-1`. This is O(k) per component instead of O(k²) pair enumeration. **0/5 sessions toward mastery (1 guided).**
- **Backward Two-Pointer Merge** — First applied via LC 88 (with guidance). When merging sorted data into a buffer with trailing empty space, fill from the back to avoid O(n) shifting per insert. Each element placed exactly once → O(m+n) time, O(1) space. Key insight: empty slots at the end are unused, so writing there never overwrites valid data. Need more practice to recognize when "fill from back" is applicable.
- **Greedy (Intervals)** — Solved 4 problems (LC 435, LC 1288, LC 56, LC 452). All severity ≤ 1 across 4 distinct days. **4/5 consecutive toward mastery.** Understand two variants:
  - **Sort by end → greedy selection** (LC 435, LC 1288): sort by end time, greedily keep the interval with earliest end. Used for maximum non-overlapping intervals / minimum removals.
  - **Sort by start → merge/group overlapping** (LC 56, LC 452): sort by start time, single-pass. Each interval either extends the current merged range or starts a new one. Used for combining all overlapping intervals and minimum arrows/groups.
  Key decision framework: "Do I need to **combine** overlapping intervals (sort by start) or **select** non-overlapping ones (sort by end)?"
  **LC 452 lesson:** Track the intersection window `[xs, xe]`. The partial overlap case (new balloon starts within window but ends past it) requires no update — the sort guarantees future balloons have `start >= current start`, so only the right endpoint matters for future overlap checks.
- **1D Dynamic Programming** — First independent application via LC 198 (slow pass, 41:56). Core recurrence: `dp[i] = max(dp[i-1], dp[i-2] + nums[i])`. Two sliding variables replace the full DP table. Struggled to identify the right DP states — spent ~42 minutes experimenting with parity-based bucket tracking before arriving at a correct but non-standard formulation. **Key framework for faster state identification:** (1) What does `dp[i]` **mean**? (2) What answers from before does `dp[i]` **depend on**? Should take ≤2 minutes to fill in. **1/5 sessions toward mastery.**
- **Binary Lifting** — First application via LC 3534 (guided). Sparse table for answering "shortest path" queries on sorted array graphs in O(log n). Key template:
   1. Sort nodes by value, compute `reach[i]` (farthest position in one jump) via binary search
   2. Build sparse table: `jump[0] = reach`, `jump[k][i] = jump[k-1][jump[k-1][i]]`
   3. Per query: greedy from largest k downward, only take jump if `jump[k][a] < b` (guard prevents overshoot)
   **Key lesson:** Initially fell for a false "diameter ≤ 2" proof that broke on counterexample `[0, 8, 14, 18]` with maxDiff=8 (distance = 3, no single intermediate node bridges). Always verify graph diameter claims with a concrete path-trace before committing to an algorithm. **1/5 sessions toward mastery.**
- **Stack** — First application via LC 20 (independent, slow pass). Core idea: use LIFO to match opening/closing brackets. Key insight: push opening brackets onto stack; on closing bracket, check top for valid pair, pop if match, else fail. Early exit: odd-length strings are always invalid. Helper closure (`pair`) cleanly handles multiple bracket types. **1/5 sessions toward mastery.**
- **Two Pointers (Fast/Slow)** — First application via LC 141 (guided, severity 3). Floyd's cycle detection: slow pointer moves 1 step, fast pointer moves 2 steps. If a cycle exists, they will meet. Initially tried a hash map keyed on `(value, index)` which failed because it tracked traversal position rather than node identity — the same node appears at different positions when revisited in a cycle. Key insight: in linked structures, always track the **node object** (pointer), not the **node value**. Values can repeat across different nodes; only the pointer uniquely identifies a node. **0/5 sessions toward mastery (guided).**
- **DFS** — First independent application via LC 104 (slow pass, 20:47). Recursive DFS using closure: pass depth as parameter, return `max(left, right)` from subtrees. Base case: nil node returns current depth. Natural fit for tree depth problems — call stack tracks depth for you. Initially attempted iterative traversal before switching to recursive. **1/5 sessions toward mastery (1 distinct day).**

### Weaknesses to Watch
- **Modular arithmetic / operator precedence with percent** — Recurring bug in LC 3756 (4+ occurrences in one session). Go percent operator binds tighter than multiply and plus, so the percent MOD must wrap the entire expression. Also, 10e8 is a float64 literal in Go — always use 1_000_000_007 for integer MOD. **Action:** Before writing any percent MOD, mentally parenthesize the entire expression.
- **Library function shortcut in interviews** — Tendency to reach for built-in functions (e.g., `bits.OnesCount`) when the problem is designed to teach an algorithmic pattern. For interview prep, always try to find the DP/algorithmic pattern first, then mention the built-in as a follow-up. Distinguish between "efficient solution" and "solution that demonstrates understanding."
- **DP case completeness** — Tendency to forget the "match" case in DP recurrences (only handling mismatches). Always ask: "what happens when the condition IS met?"
- **Index alignment in DP** — Confusing table indices (1-indexed) with string indices (0-indexed). Remember: `dp[i][j]` uses `word1[i-1]` and `word2[j-1]`.
- **Deriving recurrence from invariant** — Currently guessing recurrence from the example tables rather than deriving it from the invariant. Practice habit: define invariant → derive recurrence → verify with examples. Reinforced in LC 198: struggled to find DP states for 1D DP (House Robber), used parity buckets as a workaround instead of asking "what does the last decision depend on?" Two-sentence framework: (1) `dp[i]` **means** what? (2) `dp[i]` **depends on** what?

- **Shallow copy confusion** — In Go, `res := digits` copies the slice header but shares the underlying array. Modifying `res[i]` also modifies `digits[i]`. Use `slices.Clone(digits)` or `make` + `copy` when you need to avoid mutating the input.
- **Not leveraging input properties** — In LC 26, used a hash map when sorted array made it unnecessary. In LC 3532, built O(n²) adjacency list when sorted + maxDiff meant connected components are contiguous subarrays. Before coding, always ask: "What does the sorted/ordered property give me for free?" Sorted → compare neighbors, contiguous components. Ordered → can binary search. Structured → can use index arithmetic. The input's structure often eliminates the need for brute-force computation. **Action:** Add this to the pre-coding checklist: "What input property am I ignoring?"
- **Accepting unverified proofs about graph structure** — In LC 3534, accepted a claimed graph property ("diameter ≤ 2") without tracing a concrete counterexample. The "proof" sounded plausible but was subtly wrong — a single intermediate node doesn't always bridge two nodes in the same component. **Action:** Before committing to a structural claim, **always construct the worst-case example** and trace through it. If you can't build a counterexample, the claim holds. If you can, you've saved hours.
- **Binary lifting template recall** — Had 2 bugs in the binary lifting loop: wrong start position (hardcoded 0 instead of query-dependent `pos[u]`), and missing guard condition (`if jump[k][a] < b`) causing unconditional overshoot. This pattern needs to be memorized like binary search templates. **Action:** Practice the 3-line binary lifting loop template until it's muscle memory: init → for k descending → guard → take jump.
- **DFS as default for path problems** — In LC 1301, reached for brute-force DFS/backtracking when the problem involves "count paths with max score." DFS enumerates all paths (exponential) when DP can compute the same information in O(N²). Need to ask: "Do I need to enumerate paths, or just compute their properties?" If the latter, DP is the right tool.
- **Ignoring shifting cost in array operations** — In LC 88, used sort.Search + shifting loop which appears O(n log n) but is actually O(n*m) due to the O(m) shift per insert. Before coding, always analyze the full cost including data movement, not just the "clever" part. Ask: "What's the cost of the non-obvious operations (shifts, copies, allocations)?"
- **Identity vs value confusion in linked structures** — In LC 141, used a hash map keyed on `(value, index)` to detect cycles, which fails because values can repeat across different nodes — only the pointer uniquely identifies a node. When working with linked lists, always think in terms of node objects, not their contents. If you need to track "visited" nodes, use a map with `*ListNode` as the key (Go pointers are comparable).
- **Sort + Hash Map (coordinate compression) pattern** — Couldn't independently recognize that "assign ranks based on sorted order" maps to sort + hash map. Went for complex arithmetic instead. Need to internalize: when the problem asks "rank" or "position in sorted order," the pattern is: sort a copy → build `map[value] = rank` (dedup on the way) → map back. This is O(n log n) and works for any value range.

### Constraint-Based Algorithm Selection (Reference)
| Constraint Size | Complexity Target | Algorithm Family |
|---|---|---|
| n ≤ 10⁴ | O(n²) | Brute force, nested loops |
| n ≤ 10⁵ | O(n log n) | Sorting, binary search, two pointers |
| n ≤ 10⁶ | O(n) | Sliding window, hash map, BFS/DFS |
| n ≤ 10⁷ | O(n) | Linear scan, monotonic stack |
| n ≤ 10⁸ | O(n log n) | Rare, usually requires optimization tricks |
