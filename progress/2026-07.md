### LC 2812 - Find the Safest Path in a Grid (Medium)

**Pattern:** Multi-source BFS + Binary Search + DFS/BFS Reachability

**Approach:**
1. Compute safety grid using multi-source BFS from all thieves simultaneously — each cell stores the minimum Manhattan distance to the nearest thief
2. Binary search on the safeness factor threshold (range: 0 to max safety value)
3. For each threshold, use DFS to check if a path exists from (0,0) to (n-1,n-1) where every cell has safety ≥ threshold

**Key Learning:**
- **Greedy fails for "maximize the minimum" problems:** Initial approach picked the neighbor with the highest safety factor at each step — this makes locally optimal choices that lead to globally suboptimal paths. Traced through example 6 to understand why.
- **Binary search on the answer:** Recognized the monotonicity property — if a path exists with safety ≥ k, then a path exists with safety ≥ k-1. This makes binary search applicable.
- **Multi-source BFS:** Starting BFS from all thieves simultaneously gives the minimum distance to any thief in O(n²), much better than the brute-force O(n² × T) approach.
- **New pattern identified:** "Maximize the minimum" → binary search + feasibility check

**Weaknesses Identified:**
- **Greedy instinct:** Tendency to reach for greedy pathfinding when the problem requires global optimization. Need to ask: "Is the locally optimal choice also globally optimal?"
- **(0,0) not marked as visited in DFS:** Minor correctness gap — the starting cell was never marked visited, causing redundant exploration. Not a wrong-answer bug in practice, but a correctness issue.
- **DFS stack depth:** Using recursion for reachability check could cause stack overflow for large grids (n=400). BFS would be safer.

**Honest Self-Assessment:**
- Started with greedy approach (failed) → pivoted to multi-source BFS + binary search with guidance
- Good progress on understanding WHY greedy fails (traced example 6)
- The "maximize the minimum" → binary search pattern is new — need to internalize this

**Complexity:**
- Time: O(n² log n) — O(n²) for safety grid, O(log n) binary search steps, O(n²) DFS per step
- Space: O(n²) — safety grid and visited array

**Status:** Solved ✓ (with guidance on pattern recognition)

### LC 739 - Daily Temperatures (Medium)

**Pattern:** Monotonic Stack (Decreasing)

**Approach:**
1. Maintain a decreasing stack of `[index, temperature]` pairs
2. For each new temperature, pop all stack elements with smaller temps (they found their warmer day)
3. Set `res[poppedIndex] = currentIndex - poppedIndex`
4. Push current `[index, temp]` onto the stack
5. Remaining elements on the stack get 0 (default)

**Trace (Example 1):** `[73,74,75,71,69,72,76,73]`
```
i=0: push [0,73]          stack=[(0,73)]
i=1: 74>73→pop, res[0]=1   stack=[(1,74)]
i=2: 75>74→pop, res[1]=1   stack=[(2,75)]
i=3: 71<75→push            stack=[(2,75),(3,71)]
i=4: 69<71→push            stack=[(2,75),(3,71),(4,69)]
i=5: 72>69→pop,res[4]=1; 72>71→pop,res[3]=2  stack=[(2,75),(5,72)]
i=6: 76>72→pop,res[5]=1; 76>75→pop,res[2]=4  stack=[(6,76)]
i=7: 73<76→push            stack=[(6,76),(7,73)]
→ res=[1,1,4,2,1,1,0,0] ✓
```

**Key Learning:**
- **Monotonic stack pattern recognized and applied correctly** — this is a new pattern for the toolkit
- **Decreasing vs increasing stack decision:** Spent significant time (27 min total) figuring out which direction. Established framework: "next greater" → decreasing stack, "next smaller" → increasing stack
- **Pattern naming:** This belongs to the "Next Greater/Smaller Element" family (LC 496, 503, 739, 84, 901)

**Weaknesses Identified:**
- **Monotonic stack direction confusion:** Need to internalize the framework for choosing decreasing vs increasing. The mnemonic: "the stack holds items waiting — an element gets resolved when something opposite arrives."
- **Stack data structure choice:** Used `[][]int{}` (slice of 2-element slices) which works but is unconventional. A struct or two separate stacks would be cleaner.

**Honest Self-Assessment:**
- Algorithm: Correct, O(n) time/space — optimal solution
- Code: Clean core logic (while loop + push), well-commented with visual traces
- Speed: 27 min — most time spent on direction confusion, not on implementation
- The monotonic stack pattern is now a known tool — next time should be much faster

**Complexity:**
- Time: O(n) — each element pushed and popped at most once
- Space: O(n) — stack size

**Status:** Solved ✓

### LC 901 - Online Stock Span (Medium)

**Pattern:** Monotonic Stack (Decreasing) — second application

**Approach (Final — Span-based):**
1. Maintain a decreasing stack of `(price, span)` pairs
2. For each new price, pop all entries with `price >= stack.top.price`, accumulating their spans
3. Push `(price, accumulated_span)` onto the stack
4. Return the accumulated span

**Trace (Example 1):** `[100, 80, 60, 70, 60, 75, 85]`
```
next(100): span=1, push (100,1)     stack=[(100,1)]
next(80):  80<100, push (80,1)      stack=[(100,1),(80,1)]         → 1 ✓
next(60):  60<80, push (60,1)       stack=[(100,1),(80,1),(60,1)]  → 1 ✓
next(70):  70≥60→pop,span=2         stack=[(100,1),(80,1),(70,2)]  → 2 ✓
next(60):  60<70, push (60,1)       stack=[(100,1),(80,1),(70,2),(60,1)] → 1 ✓
next(75):  75≥60→span=2, 75≥70→span=4  stack=[(100,1),(80,1),(75,4)] → 4 ✓
next(85):  85≥75→span=5, 85≥80→span=6  stack=[(100,1),(85,6)]      → 6 ✓
```

**Approach (First Attempt — Incorrect):**
- Used two data structures: `stack` + `highestRecords`, plus a `temp` array
- Popped entries moved to `highestRecords`, then scanned full `highestRecords` for nearest barrier
- Correct output but O(n²) — O(n) scan per call, `highestRecords` never shrinks
- Removed on rewrite

**Key Learning:**
- **Monotonic stack direction framework solidified:** "Nearest greater" → decreasing stack (pop when `current >= top`). Same direction as LC 739. The framework from LC 739 applied directly.
- **Two implementation styles for monotonic stack:**
  - *Span-based* (used here): Store `(value, span)`, absorb popped spans. Best for count/distance answers.
  - *Index-based* (LeetCode's official solution): Store indices, compute `len(array) - barrier_index - 1`. Best when you need to identify the actual barrier element.
- **Invariant-first design:** Before coding, state "my stack maintains ___ from bottom to top." The popping rule is the *only* thing that preserves the invariant. Don't solve by mechanics ("move data where"), solve by invariant.
- **Minimum viable data structure:** Final struct needed only `(price, span)`. First attempt had `(day, val)` plus a whole second list. Before implementing, ask: "What's the fewest fields I need?"

**Weaknesses Identified:**
- **Over-engineering (recurring):** First attempt built unnecessary complexity (`highestRecords`, `temp`, linear scan). Same pattern as LC 14 and LC 1268. Root cause: thinking about mechanics instead of invariants.
- **O(n²) disguised as O(n):** The `highestRecords` scan made the solution quadratic, but the code complexity obscured this. Always trace the complexity of each operation.

**Honest Self-Assessment:**
- First attempt: Correct output, but over-engineered and inefficient (O(n²))
- Rewrote to classic approach after review — clean, correct, O(1) amortized
- Asked the right conceptual question ("how do I know increasing vs decreasing?") — shows growth in thinking about *why*, not just *how*
- Compared with LeetCode's official solution — good practice for flexibility
- Monotonic stack is now a solid pattern in the toolkit (2 problems solved)

**Complexity (Final Solution):**
- Time: O(1) amortized — each element pushed and popped at most once
- Space: O(n) — stack size (worst case: strictly decreasing sequence)

**Status:** Solved ✓ (rewrote from over-engineered first attempt)

### LC 3620 - Network Recovery Pathways (Hard)

**Pattern:** Binary Search on Answer + Topo Sort + DAG DP

**Approach:**
1. **Recognized "maximize the minimum" pattern** — same as LC 2812. Binary search on edge weight threshold `mid`, check if there exists a valid path from 0 to n-1 where every edge has weight ≥ `mid` AND total cost ≤ k.
2. **Feasibility check** for each threshold:
   - DFS topo sort, only following edges with weight ≥ threshold
   - Forward DP: `dp[v]` = minimum total cost to reach `v` from node 0 using only edges with weight ≥ threshold
   - Feasible if `dp[n-1] ≤ k`
3. Binary search range: [0, max_edge_weight]

**Key Learning:**
- **Pattern recognition from LC 2812 transferred directly** — "maximize the minimum" → binary search + feasibility check. This is the second time applying this pattern.
- **DAG topo sort + DP is a reusable building block** — the core engine (topo sort → forward DP) is the same as shortest-path on DAG, just wrapped in a binary search.
- **Consistency between DFS filtering and DP filtering** — the DFS filters edges by threshold for topo order, but the DP must also filter by the same threshold. Forgetting this caused a subtle bug where "illegal" edges contributed to cost.
- **Post-order DFS topo sort: no need to reverse** — push after visiting all neighbors gives topological order directly when popping from stack. Reversing it breaks the order.
- **Map vs slice performance for large inputs** — using `map[int][]edge` and `map[int]bool` for adjacency list and visited caused TLE on large inputs. Converting to `[][]edge` and `[]bool` slices fixed it.

**Weaknesses Identified:**
- **DP objective confusion** — initially computed min-cost path (shortest path DP) instead of recognizing the "maximize the minimum" binary search pattern. The problem asks for max-min-edge, not min-total-cost.
- **Consistent filtering across DFS and DP** — when a threshold filters edges in one place, it must filter in ALL places. The DFS and DP must use the same edge set.
- **Overflow in DP with MaxInt sentinel** — when `dp[u] = MaxInt` (unreachable), adding edge weight causes integer overflow → wraps to negative → incorrect feasibility. Must guard: `if dp[u] != MaxInt { relax }`.
- **Topo sort direction confusion** — spent time on whether to reverse post-order DFS result. Established rule: post-order push → pop from stack = topological order (NO reverse needed).

**Official Solution Comparison:**
- **Pre-computed topo order** — Official computes topo sort ONCE, reuses across all binary search iterations. My solution recomputes it every time. Since graph structure doesn't change (only edge filtering changes), topo order is constant. This reduces from O(log(maxW) × (V + E)) to O(V + E + log(maxW) × E). **Key general insight: separate what's constant from what changes.**
- **Kahn's algorithm (BFS)** — Official uses BFS-based topo sort (iterative, no recursion). My DFS version works but risks stack overflow on deep chains. Kahn's is the safer default.
- **Early termination** — Official stops DP when reaching n-1 (`if u == n-1 { return }`). No need to process remaining nodes.
- **Early exit** — `if !check(0) { return -1 }` before binary searching.

**Honest Self-Assessment:**
- Started with completely wrong DP objective (min-cost path), needed full restructuring around binary search
- Pattern recognition from LC 2812 was slow — had to be reminded this is the same "maximize the minimum" pattern
- Multiple subtle bugs (overflow, filtering consistency, topo sort direction) — good debugging practice
- Performance optimization (map→slice) was a new learning about data structure choice for competitive programming constraints
- Should learn to separate static computation (topo sort) from parameterized computation (DP filtering) for optimization

**Complexity:**
- Time: O(log(maxEdgeWeight) × (V + E)) — binary search × (topo sort + DP)
- Space: O(V + E) — adjacency list, visited array, DP array

**Status:** Solved ✓ (with guidance on pattern recognition + performance optimization)

### LC 2492 - Minimum Score of a Path Between Two Cities (Medium)

**Pattern:** BFS / Connected Component Traversal

**Approach:**
1. Build adjacency list from roads (bidirectional edges)
2. BFS from city 1 (node 0), tracking the minimum edge weight seen across ALL edges in the connected component
3. The answer is the minimum edge weight in city 1's connected component — because the problem allows revisiting nodes and edges, you can always construct a path from 1 to n that includes any edge in the component

**Key Learning:**
- **Connected component insight:** The minimum score path between cities 1 and n is simply the minimum edge weight in city 1's connected component. You don't need to enumerate paths — reachability suffices.
- **`if !visited[neighbor]` pattern vs `if visited[neighbor] { continue }`:** The canonical BFS template separates edge processing from enqueueing:
  ```go
  for _, v := range adj[node] {
      // Always process the edge (e.g., update minScore)
      if v.dist < minScore { minScore = v.dist }
      // Only gate enqueueing
      if !visited[v.to] {
          visited[v.to] = true
          queue = append(queue, v.to)
      }
  }
  ```
  The `continue`-based version conflates edge processing with enqueue control, making it impossible to process edges to already-visited nodes. Adopt `if !visited` as default BFS template.
- **Node-visited vs edge-visited:** For problems that only need connectivity (reach all nodes), `[]bool` node-visited is sufficient and much faster than `map[Edge]bool` edge-visited. Edge-level visited is only needed when you must enumerate distinct paths.
- **Map vs array for visited tracking:** `map[road]bool` with struct keys is significantly slower than `[]bool` array indexing — the primary cause of the original TLE.

**Weaknesses Identified:**
- **TLE debugging instinct:** When facing TLE, the student's first instinct was to change the map key type (from node to road struct), which didn't address the root cause. Should first ask: "Is my data structure choice the bottleneck, or is my algorithm visiting too much?"
- **Mental model gap on `continue`:** Initially assumed `if visited[v.to] { continue }` was equivalent to node-based visited tracking — missed that `continue` skips ALL edge processing, not just enqueueing. The `if !visited` template avoids this class of bug.
- **BFS vs backtracking decision:** The problem says "path" but the answer depends on the entire connected component (min edge weight). Recognized that BFS with node visited suffices when the answer is a component-level property, not a path-enumeration task.

**Honest Self-Assessment:**
- Core BFS approach was correct from the start — the algorithm was right, the data structure choice caused TLE
- The `map[road]bool` was doubly problematic: slow hashing AND structural issue (bidirectional edges had different keys)
- After clarification, immediately understood and implemented the fix — good conceptual flexibility
- The BFS template habit (`if !visited`) is a concrete takeaway for future problems

**Complexity:**
- Time: O(V + E) — each node and edge processed once
- Space: O(V + E) — adjacency list and visited array

**Status:** Solved ✓ (with guidance on data structure choice and BFS template)
