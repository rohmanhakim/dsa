### LC 2812 - Find the Safest Path in a Grid (Medium)

**Pattern:** Multi-source BFS + Binary Search + DFS/BFS Reachability

**Approach:**
1. Compute safety grid using multi-source BFS from all thieves simultaneously — each cell stores the minimum Manhattan distance to the nearest thief
2. Binary search on the safeness factor threshold (range: 0 to max safety value)
3. For each threshold, use DFS to check if a path exists from (0,0) to (n-1,n-1) where every cell has safety ≥ threshold

**Key Learning:**
- **Greedy fails for "maximize the minimum" problems:** Initial approach picked the neighbor with the highest safety factor at each step — this makes locally optimal choices that lead to globally suboptimal paths. Traced through example 6 to understand why.
- **Binary search on the answer:** Recognized the monotonicity property — if a path exists with safety ≥ k, then a path exists with safety ≥ k-1. This makes binary search applicable.
- **Multi-source BFS:** Starting BFS from all thieves simultaneously gives the minimum distance to any thief in O(n²), much better than the brute-force O(n² × T) approach.
- **New pattern identified:** "Maximize the minimum" → binary search + feasibility check

**Weaknesses Identified:**
- **Greedy instinct:** Tendency to reach for greedy pathfinding when the problem requires global optimization. Need to ask: "Is the locally optimal choice also globally optimal?"
- **(0,0) not marked as visited in DFS:** Minor correctness gap — the starting cell was never marked visited, causing redundant exploration. Not a wrong-answer bug in practice, but a correctness issue.
- **DFS stack depth:** Using recursion for reachability check could cause stack overflow for large grids (n=400). BFS would be safer.

**Honest Self-Assessment:**
- Started with greedy approach (failed) → pivoted to multi-source BFS + binary search with guidance
- Good progress on understanding WHY greedy fails (traced example 6)
- The "maximize the minimum" → binary search pattern is new — need to internalize this

**Complexity:**
- Time: O(n² log n) — O(n²) for safety grid, O(log n) binary search steps, O(n²) DFS per step
- Space: O(n²) — safety grid and visited array

**Status:** Solved ✓ (with guidance on pattern recognition)

### LC 17 - Letter Combinations of a Phone Number (Medium)

**Pattern:** Backtracking / Recursion, Cartesian Product

**Approach:**
1. **Iterative (first attempt):** Built letter pool via loop, then iteratively computed cartesian product — each new digit extends all existing combinations with its letters
2. **Backtracking (second attempt):** DFS on a tree of choices — at each digit position, try each letter, recurse to next digit, backtrack after

**Key Learning:**
- **Backtracking pattern:** `append → recurse → pop` is the standard structure. Each level of recursion corresponds to one decision point (one digit), each branch is one choice (one letter). Base case: when `len(path) == len(digits)`, save the combination.
- **Phone mapping simplicity:** Learned (again) to use a constant array literal (`[]string{"", "abc", "def", ...}`) instead of deriving it programmatically. The loop-based approach was over-engineered.
- **Two valid approaches:** Iterative cartesian product and backtracking DFS both work. Backtracking is more generalizable (permutations, subsets, N-Queens, etc.).

**Weaknesses Identified:**
- **Over-engineering (recurrence):** The iterative version built the phone mapping with a complex loop + conditional increments instead of a simple array literal. This is the same over-engineering weakness seen in LC 14 and LC 1268. The fix is asking: "What's the minimum I need to compute?" before coding.

**Honest Self-Assessment:**
- Iterative solution: correct but pool building was unnecessarily complex
- Backtracking solution: clean, correct, follows standard pattern — clear improvement
- Successfully learned the backtracking pattern and applied it independently
- Phone mapping improvement shows growing awareness of over-engineering tendency

**Complexity:**
- Time: O(3^n × 4^m) — n = digits with 3 letters, m = digits with 4 letters
- Space: O(3^n × 4^m) — for the result

**Status:** Solved ✓ (both approaches)

### LC 739 - Daily Temperatures (Medium)

**Pattern:** Monotonic Stack (Decreasing)

**Approach:**
1. Maintain a decreasing stack of `[index, temperature]` pairs
2. For each new temperature, pop all stack elements with smaller temps (they found their warmer day)
3. Set `res[poppedIndex] = currentIndex - poppedIndex`
4. Push current `[index, temp]` onto the stack
5. Remaining elements on the stack get 0 (default)

**Trace (Example 1):** `[73,74,75,71,69,72,76,73]`
```
i=0: push [0,73]          stack=[(0,73)]
i=1: 74>73→pop, res[0]=1   stack=[(1,74)]
i=2: 75>74→pop, res[1]=1   stack=[(2,75)]
i=3: 71<75→push            stack=[(2,75),(3,71)]
i=4: 69<71→push            stack=[(2,75),(3,71),(4,69)]
i=5: 72>69→pop,res[4]=1; 72>71→pop,res[3]=2  stack=[(2,75),(5,72)]
i=6: 76>72→pop,res[5]=1; 76>75→pop,res[2]=4  stack=[(6,76)]
i=7: 73<76→push            stack=[(6,76),(7,73)]
→ res=[1,1,4,2,1,1,0,0] ✓
```

**Key Learning:**
- **Monotonic stack pattern recognized and applied correctly** — this is a new pattern for the toolkit
- **Decreasing vs increasing stack decision:** Spent significant time (27 min total) figuring out which direction. Established framework: "next greater" → decreasing stack, "next smaller" → increasing stack
- **Pattern naming:** This belongs to the "Next Greater/Smaller Element" family (LC 496, 503, 739, 84, 901)

**Weaknesses Identified:**
- **Monotonic stack direction confusion:** Need to internalize the framework for choosing decreasing vs increasing. The mnemonic: "the stack holds items waiting — an element gets resolved when something opposite arrives."
- **Stack data structure choice:** Used `[][]int{}` (slice of 2-element slices) which works but is unconventional. A struct or two separate stacks would be cleaner.

**Honest Self-Assessment:**
- Algorithm: Correct, O(n) time/space — optimal solution
- Code: Clean core logic (while loop + push), well-commented with visual traces
- Speed: 27 min — most time spent on direction confusion, not on implementation
- The monotonic stack pattern is now a known tool — next time should be much faster

**Complexity:**
- Time: O(n) — each element pushed and popped at most once
- Space: O(n) — stack size

**Status:** Solved ✓

### LC 901 - Online Stock Span (Medium)

**Pattern:** Monotonic Stack (Decreasing) — second application

**Approach (Final — Span-based):**
1. Maintain a decreasing stack of `(price, span)` pairs
2. For each new price, pop all entries with `price >= stack.top.price`, accumulating their spans
3. Push `(price, accumulated_span)` onto the stack
4. Return the accumulated span

**Trace (Example 1):** `[100, 80, 60, 70, 60, 75, 85]`
```
next(100): span=1, push (100,1)     stack=[(100,1)]
next(80):  80<100, push (80,1)      stack=[(100,1),(80,1)]         → 1 ✓
next(60):  60<80, push (60,1)       stack=[(100,1),(80,1),(60,1)]  → 1 ✓
next(70):  70≥60→pop,span=2         stack=[(100,1),(80,1),(70,2)]  → 2 ✓
next(60):  60<70, push (60,1)       stack=[(100,1),(80,1),(70,2),(60,1)] → 1 ✓
next(75):  75≥60→span=2, 75≥70→span=4  stack=[(100,1),(80,1),(75,4)] → 4 ✓
next(85):  85≥75→span=5, 85≥80→span=6  stack=[(100,1),(85,6)]      → 6 ✓
```

**Approach (First Attempt — Incorrect):**
- Used two data structures: `stack` + `highestRecords`, plus a `temp` array
- Popped entries moved to `highestRecords`, then scanned full `highestRecords` for nearest barrier
- Correct output but O(n²) — O(n) scan per call, `highestRecords` never shrinks
- Removed on rewrite

**Key Learning:**
- **Monotonic stack direction framework solidified:** "Nearest greater" → decreasing stack (pop when `current >= top`). Same direction as LC 739. The framework from LC 739 applied directly.
- **Two implementation styles for monotonic stack:**
  - *Span-based* (used here): Store `(value, span)`, absorb popped spans. Best for count/distance answers.
  - *Index-based* (LeetCode's official solution): Store indices, compute `len(array) - barrier_index - 1`. Best when you need to identify the actual barrier element.
- **Invariant-first design:** Before coding, state "my stack maintains ___ from bottom to top." The popping rule is the *only* thing that preserves the invariant. Don't solve by mechanics ("move data where"), solve by invariant.
- **Minimum viable data structure:** Final struct needed only `(price, span)`. First attempt had `(day, val)` plus a whole second list. Before implementing, ask: "What's the fewest fields I need?"

**Weaknesses Identified:**
- **Over-engineering (recurring):** First attempt built unnecessary complexity (`highestRecords`, `temp`, linear scan). Same pattern as LC 14 and LC 1268. Root cause: thinking about mechanics instead of invariants.
- **O(n²) disguised as O(n):** The `highestRecords` scan made the solution quadratic, but the code complexity obscured this. Always trace the complexity of each operation.

**Honest Self-Assessment:**
- First attempt: Correct output, but over-engineered and inefficient (O(n²))
- Rewrote to classic approach after review — clean, correct, O(1) amortized
- Asked the right conceptual question ("how do I know increasing vs decreasing?") — shows growth in thinking about *why*, not just *how*
- Compared with LeetCode's official solution — good practice for flexibility
- Monotonic stack is now a solid pattern in the toolkit (2 problems solved)

**Complexity (Final Solution):**
- Time: O(1) amortized — each element pushed and popped at most once
- Space: O(n) — stack size (worst case: strictly decreasing sequence)

**Status:** Solved ✓ (rewrote from over-engineered first attempt)
